### **Анализ предметной области. Выставление требований к ПС. User Story, Acceptance Criteria и Definition of Done**

---

### **1. Анализ предметной области**

**Анализ предметной области** — это этап жизненного цикла программного средства, на котором изучается сфера применения будущей системы, определяются цели, проблемы и задачи, которые она должна решать. Основной результат этого этапа — ясное понимание требований и особенностей системы.

На этапе анализа предметной области:
- Идентифицируются ключевые процессы, данные и участники системы.
- Выявляются ограничения и требования (функциональные и нефункциональные).
- Анализируются аналоги и конкуренты.
- Определяются пользователи системы и их потребности.

---

### **2. Выставление требований к программному средству (ПС)**

Для создания успешного программного продукта важно правильно формулировать и документировать требования.  
**Требования** делятся на:
- **Функциональные** (что система должна делать: примеры функций, логика работы).
- **Нефункциональные** (ограничения: производительность, безопасность, масштабируемость и т.д.).
- **Бизнес-требования** (цели, которых бизнес хочет достичь).

Основные методы выставления требований:
- Интервью с клиентами и пользователями.
- Проведение воркшопов.
- Использование фреймворков (например, User Story или Use Case).

---

### **3. User Story (Пользовательская история)**

**User Story** — это инструмент Agile-разработки, используемый для формулировки требований с точки зрения пользователя. Это краткое описание функции или задачи, которую пользователь хочет выполнить, написанное простым языком.

**Формат User Story**:  
```plaintext
Как <тип пользователя>, я хочу <функциональность>, чтобы <цель>.
```

**Пример User Story**:
- Как **покупатель**, я хочу **получить уведомление о скидках**, чтобы **сэкономить деньги при покупке**.

#### **Преимущества User Story**:
- Простота и понятность.
- Фокус на потребностях пользователя.
- Гибкость (может быть дополнена или изменена в процессе работы).

#### **Компоненты User Story**:
1. **Описание**: Четкая формулировка пользовательского сценария.
2. **Acceptance Criteria (Критерии приемки)**: Условия, при выполнении которых User Story считается завершенной.
3. **Оценка**: Затраты времени и ресурсов на выполнение задачи.

---

### **4. Acceptance Criteria (Критерии приемки)**

**Acceptance Criteria (AC)** — это набор четких, измеримых условий, которые должны быть выполнены, чтобы User Story считалась завершенной.  

**Цель AC**:
- Проверить, что реализованная функциональность соответствует требованиям.
- Определить границы и объем User Story.

**Пример Acceptance Criteria**:
Для User Story:  
*Как покупатель, я хочу получить уведомление о скидках, чтобы сэкономить деньги при покупке.*

**AC**:
1. Пользователь получает уведомление о скидках в формате e-mail.
2. Уведомление содержит список товаров со скидкой.
3. Скидки отображаются корректно, в соответствии с настройками пользователя.
4. Уведомление отправляется не чаще 1 раза в неделю.

---

### **5. Definition of Done (DoD)**

**Definition of Done (DoD)** — это согласованный список критериев, который определяет, когда задача или User Story считается завершенной.

**DoD включает**:
- Завершение всех задач, связанных с User Story (код, тестирование, документация).
- Проверку на соответствие критериям приемки (AC).
- Рецензирование и утверждение изменений (например, код-ревью).
- Успешное развертывание изменений в тестовую среду.
- Обновление документации (при необходимости).

**Пример DoD**:
1. Код написан, протестирован и успешно прошел код-ревью.
2. Реализованы все Acceptance Criteria.
3. Изменения развернуты в тестовой среде и проверены.
4. Автоматизированные тесты добавлены, и все тесты проходят успешно.
5. Документация обновлена (если применимо).

---

### **6. Различие между Acceptance Criteria и Definition of Done**

| **Критерий**           | **Acceptance Criteria (AC)**                                         | **Definition of Done (DoD)**                          |
|-------------------------|----------------------------------------------------------------------|-------------------------------------------------------|
| **Цель**               | Определяет, что конкретно нужно сделать для выполнения User Story.  | Определяет, что необходимо сделать для завершения работы. |
| **Уровень детализации** | Конкретно для одной User Story.                                     | Общий для всех User Story/задач.                     |
| **Применимость**        | Проверяет соответствие функциональности ожиданиям пользователя.    | Охватывает весь процесс разработки, включая тестирование и развертывание. |
| **Пример**             | "Пользователь может войти в систему через e-mail и пароль."         | "Код протестирован, проверен, развернут и документация обновлена." |

---

### **Заключение**

Выставление требований — это ключевой этап разработки ПС. **User Story**, **Acceptance Criteria** и **Definition of Done** обеспечивают четкое понимание того, что нужно сделать, как это должно работать и когда работа считается завершенной. Это снижает риск недоразумений между разработчиками, тестировщиками и заказчиками, что особенно важно в Agile-подходах.
